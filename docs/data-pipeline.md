# Data Pipeline Architecture and Design
## AI Agents Tracking & Observability Platform

## 1. Overview

The platform aims to monitor AI agent executions by collecting structured telemetry data, including:

- Agent and model information
- Execution traces and spans
- Token usage
- Tool calls
- Operation timestamps and durations
- Execution status
- Benchmark and session metadata

The data pipeline follows the **Medallion Architecture**, organized into three layers:

- **Bronze:** Raw data ingestion and preservation.
- **Silver:** Data cleaning, validation, and transformation.
- **Gold:** Aggregated and analysis-ready datasets.

The pipeline is designed to support both historical public datasets and telemetry collected from live AI agents.

## 2. Data Sources

The platform uses two main data sources.

### 2.1 Public Dataset

The initial historical data source is the [Exgentic/agent-llm-traces](https://huggingface.co/datasets/Exgentic/agent-llm-traces) dataset available on Hugging Face.

It contains execution traces collected from different agent harnesses, models, and benchmarks.

Dataset characteristics identified during exploration:

| Metric | Value |
|---|---:|
| Parquet files | 39 |
| Session records | 1,781 |
| Total spans | 38,052 |
| Unique session IDs | 1,781 |
| Unique trace IDs | 1,781 |

The dataset is used to explore agent execution behavior, understand the telemetry schema, and prepare historical data for the platform.

For additional details, see [dataset-documentation.md](dataset-documentation.md).

### 2.2 Live Agent Telemetry

The second source consists of telemetry generated by AI agents during live execution.

The planned collection architecture includes:

1. An instrumented AI agent generates telemetry.
2. A Python SDK, framework callback, or OpenTelemetry instrumentation captures supported execution events.
3. The telemetry is sent to a FastAPI backend.
4. The backend validates incoming data and stores operational records in PostgreSQL.
5. The data can then be made available to the analytical pipeline.

The collection mechanism depends on the agent framework and the instrumentation supported by the agent.

**Important:** The platform does not automatically observe arbitrary agents. Agents must expose compatible telemetry through an SDK, API, callbacks, framework hooks, or OpenTelemetry instrumentation.

The platform focuses on observable execution metadata and events. It does not require collecting private model reasoning or hidden chain-of-thought.

The data pipeline combines historical public traces and live-agent telemetry into a common analytical structure.

This diagram represents the intended logical data flow. The live collection backend and the analytical medallion pipeline are separate components connected through data ingestion.

### 3.2 Data Flow Principles

The pipeline follows these principles:

- Preserve the original data before applying transformations.
- Maintain traceability between raw and processed records.
- Apply consistent validation rules.
- Normalize data from different sources into a shared schema.
- Preserve source information and provenance.
- Prepare structured data for downstream analytics and machine learning.

## 4. Bronze Layer — Raw Data

### 4.1 Purpose

The Bronze layer stores ingested data in its original or minimally transformed form.

Its main objective is to preserve the original information and provide a reliable starting point for downstream processing.

### 4.2 Data Ingestion

The Bronze layer receives data from:

- Public historical datasets.
- Live-agent telemetry made available by the backend.

For the public dataset, the original Parquet records are ingested from the Hugging Face source.

For live telemetry, the ingestion process retrieves records from the operational collection system.

### 4.3 Main Operations

- Load source files or telemetry records.
- Preserve the original structure and fields.
- Record ingestion metadata.
- Identify the source of each dataset.
- Store the raw data in a structured format.
- Avoid destructive cleaning at ingestion time.

### 4.4 Recommended Metadata

Each ingested record or dataset should preserve relevant provenance information, such as:

| Field | Description |
|---|---|
| `source_type` | Origin of the data, such as `public_dataset` or `live_agent` |
| `source_name` | Dataset name or originating agent/service |
| `ingestion_timestamp` | Time when the data was ingested |
| `source_file` | Original file or source reference, when applicable |
| `session_id` | Session identifier |
| `trace_id` | Trace identifier |

The exact metadata fields should be aligned with the common schema.

### 4.5 Storage

The Bronze layer is intended to use Parquet files for structured analytical storage.

Example directory organization:

```text
data/
└── bronze/
    ├── public_dataset/
    │   ├── traces/
    │   └── metadata/
    │
    └── live_agent/
        ├── traces/
        └── metadata/
```

The directory structure may evolve according to ingestion requirements.

## 5. Silver Layer — Cleaned and Standardized Data

### 5.1 Purpose

The Silver layer contains cleaned, validated, and standardized data.

Its objective is to transform raw telemetry into a consistent representation that can be reused by analytics and machine learning components.

### 5.2 Data Cleaning

The cleaning process may include:

- Handling missing and null values.
- Detecting malformed records.
- Validating required identifiers.
- Checking timestamp formats.
- Removing confirmed duplicate records.
- Validating numeric fields.
- Parsing serialized JSON attributes.
- Standardizing field names and data types.

Cleaning rules must be based on the meaning of each field. Missing values should not automatically be replaced with zero or empty strings.

### 5.3 Span Normalization

The public dataset contains a nested `spans` field.

For analytical processing, spans can be extracted into a separate span-level table.

For example:

**Session-level table**

| session_id | harness | benchmark | models |
|---|---|---|---|
| session_001 | claude_code | swebench | model_A |

**Span-level table**

| trace_id | span_id | session_id | type |
|---|---|---|---|
| trace_001 | span_001 | session_001 | llm_call |
| trace_001 | span_002 | session_001 | llm_call |

This structure makes it easier to analyze individual operations while preserving the relationship between sessions, traces, and spans.

### 5.4 Identifier Management

The following identifiers should be preserved:

- `session_id`: identifies a session.
- `trace_id`: identifies a complete trace.
- `span_id`: identifies an individual span within a trace.

The composite key `(trace_id, span_id)` should be used when identifying spans across the dataset.

The identifier checks performed on the public dataset found:

- No missing session IDs.
- No missing trace IDs.
- No missing span IDs.
- No repeated span IDs within the same trace.
- A one-to-one relationship between sessions and traces in the analyzed dataset.

### 5.5 JSON Parsing

Some telemetry attributes are stored as serialized JSON strings, particularly:

- `gen_ai.input.messages`
- `gen_ai.output.messages`
- `gen_ai.tool.definitions`

These fields can be parsed to extract structured information.

For example, `gen_ai.output.messages` can contain tool-call objects nested inside message parts.

The transformation process should:

1. Check whether the field is null.
2. Parse the JSON safely.
3. Validate the expected structure.
4. Extract relevant metadata.
5. Handle malformed JSON without interrupting the entire pipeline.

Sensitive message content and tool arguments should not be exposed unnecessarily.

### 5.6 Data Validation

The Silver layer should apply validation checks such as:

| Validation | Objective |
|---|---|
| Identifier validation | Ensure required identifiers are present |
| Session consistency | Check that span session IDs match their parent session |
| Trace consistency | Validate session-to-trace relationships |
| Timestamp validation | Check timestamp formats and ordering |
| Numeric validation | Verify token counts and numeric ranges |
| Duplicate detection | Identify confirmed duplicate records |
| Schema validation | Ensure expected fields and data types |

### 5.7 Storage

The Silver layer is intended to store cleaned and standardized data in Parquet format.

Example:

```text
data/
└── silver/
    ├── sessions/
    │   └── sessions.parquet
    │
    ├── traces/
    │   └── traces.parquet
    │
    └── spans/
        └── spans.parquet
```

## 6. Gold Layer — Analytics-Ready Data

### 6.1 Purpose

The Gold layer contains processed and aggregated datasets designed for analytics, dashboards, and machine learning.

It transforms standardized telemetry into meaningful indicators of agent execution behavior.

### 6.2 Potential Analytical Metrics

**Token Usage**

- Total input tokens.
- Total output tokens.
- Total tokens per session.
- Average token usage per model.
- Token usage by benchmark.

**Tool Usage**

- Total tool calls.
- Tool-call frequency.
- Most frequently used tools.
- Tool calls per session.
- Distribution of tool-call types.

**Execution Performance**

- Operation duration.
- Trace duration.
- Average duration per operation.
- Execution time by model.
- Execution time by benchmark.

Duration should be derived from `start_time` and `end_time` only after validating timestamp formats and timezone assumptions.

**Execution Status**

- Successful operations.
- Failed operations.
- Error distribution.
- Status distribution by model or benchmark.

Status-code interpretation must follow the conventions used by the source instrumentation.

### 6.3 Feature Engineering

The Gold layer can also provide features for anomaly detection.

Potential features include:

| Feature | Description |
|---|---|
| `total_input_tokens` | Total input tokens used |
| `total_output_tokens` | Total output tokens generated |
| `total_tool_calls` | Number of tool calls |
| `trace_duration` | Total trace execution duration |
| `error_count` | Number of operations marked as errors |
| `span_count` | Number of spans in a trace |
| `unique_tools_count` | Number of distinct tools used |
| `model_count` | Number of models involved |

These features can be aggregated at session or trace level, depending on the ML task.

The final feature set should be determined with the ML/MLOps team and validated against the anomaly-detection objective.

### 6.4 Storage

Example Gold organization:

```text
data/
└── gold/
    ├── token_usage/
    │   └── token_metrics.parquet
    │
    ├── tool_usage/
    │   └── tool_metrics.parquet
    │
    ├── execution_performance/
    │   └── performance_metrics.parquet
    │
    └── anomaly_features/
        └── trace_features.parquet
```
